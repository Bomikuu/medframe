# Clinic Invitation and Onboarding Implementation Plan

> **For agentic workers:** Execute natively in this chat, task by task. The user's explicit instruction overrides skill defaults requesting subagents or independent agent review. Do not delegate, create another chat, or require another choice of execution method. All tasks form one integrated delivery; checkbox/commit boundaries are implementation order, not user handoffs.

**Goal:** An invited clinic can learn about Medframe, verify its recipient, save/resume setup, establish its administrator through existing Django authentication/MFA, and create its configured clinical workspace exactly once.

**Architecture:** A restricted onboarding GraphQL schema and session-bound invitation proof authorize pre-account setup without weakening clinical GraphQL. A new Django app owns invitation/draft/logo lifecycle; finalization materializes existing organization, account, membership and branding models plus normalized configuration in one transaction. Dedicated Next.js onboarding/platform routes reuse the design system without requiring an existing clinic workspace.

**Tech Stack:** Django ORM/auth/migrations, Strawberry, PostgreSQL, Redis/Celery, encrypted MailOutbox, private Django storage/ClamAV, Next.js App Router, TypeScript, Tailwind, shadcn/ui, RHF/Zod and existing GraphQL code generation.

**Spec:** `docs/superpowers/specs/2026-10-19-medframe-clinic-onboarding-design.md`, approved by the user's “proceed.” Full source brief: `docs/requirements/medframe-clinic-onboarding.txt`.

## Global Constraints

- Native only, no subagents or delegated review. One connected feature batch, followed by local activation under standing authorization.
- Preserve original database, credentials, MFA, private files, checkpoints and `.next-selection-focus`. No push, public deployment, original clinical test writes, real-recipient messaging or clone restoration over original data.
- One accumulated targeted test pass and one batched desktop/tablet/phone inspection. Write tests alongside their owner tasks but defer execution until Task 9. Only necessary activation blockers receive one batched repair/focused confirmation. Log unrelated issues without fixing them.
- Read `AGENTS.md`, `apps/web/AGENTS.md`, installed Next guides and approved spec before implementation. Apply Impeccable craft-floor immediately before UI edits. Preserve established tokens, Manrope/Jakarta, Tailwind and actual shadcn; Prettier/Ruff format supported source.
- Tokens: 256-bit random, digest-only DB; default seven-day invite, allowed one hour–thirty days. Email code: six digits, ten minutes, five failed attempts; proofs: eight hours absolute/thirty minutes idle, bounded by invitation expiry.
- Drafts require server persistence, expected versions and owner proof. Never persist passwords, raw tokens, codes or clinical data in draft JSON, URLs, client storage, audit or logs. Only an encrypted mail payload may temporarily contain delivery secrets.
- Logos: PNG/JPEG/WebP, ≤2 MiB before/after encoding, ≤2048px each side, no SVG/animation; private quarantine/scan/authorized preview. Preserve aspect ratio. Only profile avatars are circular.
- New onboarding branding defaults: primary `#0F2D4A`, secondary `#0EA5A4`, accent `#22C1B6`; legacy saved themes remain unchanged. Preview is scoped and uses the persisted theme validator/resolver.
- No clinical role/ProviderProfile from specialty or provider selections. No website builder, AI integration, payment processing, live SMS, advanced provider schedules or staff-invitation subsystem.
- Readable versioned development-use notices are labelled as such; production needs approved configured Terms/Privacy content.

## Review Focus

1. Existing signed-in users: verifying email/session rotation must preserve their valid ClinicalSession, while an account switch must be explicit. Test in Task 3.
2. Delayed callbacks after revocation/resend: stale codes, scan jobs and pending MFA must not restore access or publish a removed logo. Tests in Tasks 2–4.
3. Uncertain saves/multiple tabs: responses arriving after another save or Save and Exit must not overwrite data, falsely show saved, or advance an invalid step. Tests in Tasks 3/7.
4. Confirmation races and dropped responses: replays return one authorized clinic; conflicting payloads, expiration and revoke/complete races never create partial/duplicate organizations. Tests in Task 5.
5. Long/incomplete inputs and narrow devices: country-aware phone, partial drafts, invalid color, logo proportions, keyboard slides, error focus and sticky actions remain usable. Tests in Tasks 6/7/9.

Keep step-local forms focused; one orchestration hook owns server snapshots and save sequencing.

Routes: `app/onboarding/layout.tsx`, `invite/[token]/page.tsx`, `setup/page.tsx`, `paused/page.tsx`, `completed/page.tsx`, `notices/[kind]/page.tsx`; `app/platform/layout.tsx` and `clinic-invitations/page.tsx`. Platform/onboarding layouts do not wrap `WorkspaceProvider`.

`contracts.py` defines `Step = Literal['clinic','specialties','branding','practice','account','review']` and `OnboardingSnapshot` (session UUID, version, current/completed steps, status, intro status, validated progress data, authorized logo metadata, verified identity, nullable completed organization UUID). `snapshot(request) -> OnboardingSnapshot` is the only owner-filtered draft serializer. JSON progress keys stay snake_case, with matching frontend Zod schemas; GraphQL object fields use normal Strawberry camelCase. `CompletionResult` contains organization_id, branch_id, membership_id and completed_at only. No serializer returns a token/code/storage key/password.

Define `BootstrapState` as validity/status, masked recipient, intro status and verification-required flag only; `LogoState` as logo UUID, scan_state, MIME/size/dimensions and current draft_version. `InvitationInput` contains normalized email, optional contact/clinic hints and expiry; `AccountInput` contains first/last name, new/existing mode, ephemeral password/confirmation and accepted notice versions. AccountInput is never a draft field. `ChecklistState` contains version, dismissed flag and known checklist IDs/states/working destinations. These shared types are implemented before their consumers, rather than invented separately in each module.
