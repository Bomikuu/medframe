## Global constraints

- “Clinic verifies identity, then issues an invitation.” Email/name/DOB/guardian text does not link an account automatically.
- “One browser session uses one realm at a time.” Reuse native Django users/passwords/sessions/MFA/recovery/CSRF; no parallel authentication database or custom bearer-token sessions.
- “Identity verification and clinical publication are separate decisions.” Clinical records require explicit release of exact versions; drafts/internal records are private by default.
- “Patient-submitted information stays separate from clinician-confirmed records.” Never auto-merge reports or template prompts into medical facts.
- “Absence must never be labeled as clinical resolution, extraction or healing.” Historical chart summaries show up to five findings per tooth and disclose that limit.
- Follow-up text ≤4,000 characters. Patient reports ≤6,000 characters and ≤12KiB UTF-8. Invitations expire after 24 hours; pending authentication remains 5 minutes; signed downloads remain ≤60 seconds; existing 8h absolute/30m idle expiry remains.
- Preserve 52 FDI teeth/260 named surface patches, exact revisions, completed procedure evidence, tenant/patient grants, audit guards, request bounds and no-store behavior. A superuser does not bypass domain policy.
- Preserve `da3d519` / `checkpoint/django-batch-1-2026-10-18`, the older checkpoint/backups, the source `medframe` DB and the active `medframe_django` data. No re-import, reset, push, publication or production deployment.
- Work natively in this checkout on `codex/django-clinical-batch-2`; use readable focused modules, Prettier/Ruff and Tailwind. Reuse actual shadcn sources; add primitives with the official CLI only if required. Circular profile media, full-framing clinical images.
- Use synthetic identities and local Mailpit for development invitation/recovery delivery; do not send invitations to real people. Keep credentials, tokens, dumps and medical values out of Git/logs/screenshots.
- Keep public websites, scheduling/queues, billing and diagnostic collaboration outside Batch 2. The anatomical model and approved product symbol remain asset boundaries, not invented substitutes.

## Review focus

1. A human who is both staff and a patient switches realms while an old request is pending: old completions must not expose private state, and patient requests must fail every staff endpoint, including files and Admin. Tasks 1, 7 and 9 test this explicitly.
2. An invitation is reissued/revoked or a password resets while two MFA claims complete: at most one valid active relationship is created, no password/MFA is overwritten, and no raw token enters a session/outbox log. Tasks 6 and 9 pin races and fail-closed recovery.
3. A clinician previews a release, then another author edits the plan/follow-up: publish only the reviewed source versions or return a conflict. Later amendments/new documents must not mutate the release. Tasks 4 and 7 test snapshot integrity and optimistic preview confirmation.
4. A fifth/sixth finding leaves a bounded historical chart, a finding is removed in an amendment, or the same tooth gains a new key: comparison must describe display changes without claiming healing. Task 2 pins these inputs.
5. A delayed preview/filter request completes after a patient/clinic change or link withdrawal; DST/date-only filters, Unicode byte limits and cancelled-plan denominators must remain correct. Tasks 3, 4, 7–9 include targeted regressions.

## Ownership and common contracts

Paths below are repository-relative. Existing canonical owners stay in place; split the large GraphQL/editor modules only where a task adds a cohesive owner.

| Owner                                                                            | Responsibility                                                                                                            |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `services/api/config/`, `medframe_apps/accounts/`, `organizations/policy.py`     | Native session realm, operational guards, invitation mail kind, scoped new permissions and safe rehearsal broker override |
| `medframe_apps/dental/history.py`, `api_graphql/dental_history.py`               | Authorized exact chart comparison and paginated tooth/procedure evidence                                                  |
| `medframe_apps/encounters/{templates,queries}.py`, `models.py`                   | Immutable template revisions/applications and authorized filtered encounter discovery                                     |
| `medframe_apps/treatments/{services,follow_ups}.py`, `models.py`                 | Immutable plan snapshots/events, safe ordering/editing and clinician follow-ups                                           |
| `medframe_apps/documents/queries.py`, existing transfer services/views           | Scoped filters and clean/version-exact transfers                                                                          |
| New `medframe_apps/portal/{models,policy,invitations,releases,reports,views}.py` | Explicit verified relationships, release snapshots, reports and portal transfer policy                                    |
| `api_graphql/{portal_schema,portal_types,portal_staff}.py`                       | Portal-only DTO/schema and separate staff management/release operations                                                   |
| `apps/web/features/{dental,consultations,treatments,documents,portal}/`          | Focused composed screens, shared read-only renderers, prompts and safe preview lifecycle                                  |
| `apps/web/lib/{graphql,server}/`, route adapters                                 | Separately generated portal operations, fixed proxy allowlists, native cookie/CSRF handling                               |

Shared new value/entity types: `SessionRealm = Literal['staff','patient']`; immutable `RecordFilter(query<=160, status/type enums, author_id?, date_from?, date_to?, tooth?)`; `RecordPage[T](items, end_cursor, has_next_page)` with default 20/max 50; `SourceVersion(kind,id,version)`; `RequestReceipt(actor,organization,operation,key,digest,result_id)` for idempotent new writes, implemented by Task 4 in the auditing app. Its uniqueness includes the server-owned operation namespace. `replay_request(actor,organization,operation,key,input_data) -> UUID|None` acquires the advisory lock/checks the canonical digest; `record_request_result(...,result_id)` inserts the immutable receipt in the same outer transaction. Domain services authorize live scope before replay and do not store clinical input in the receipt. Define these in focused Python modules with frontend Zod counterparts generated/validated at boundaries. Never treat arbitrary JSON as authorized model content.

Cursor contract: signed/bounded (≤1,024 characters) `(created_at,id)` cursor bound to organization/patient/list-kind/filter digest; decode as input, never as authorization. Sort descending by `(created_at,id)`. Invalid/mismatched cursors fail safely and UI resets pagination when filters change. Preserve legacy query signatures while new connection fields use this contract.

Lock order when those rows are required: user → patient → invitation/link → MFA/recovery → encounter/plan/follow-up/release. Re-read mutable authority after acquiring its lock; never invert a shared lock order. All clinical/portal writes and their audit events share one transaction. Use transaction-enabled tests with separate connections for races.
