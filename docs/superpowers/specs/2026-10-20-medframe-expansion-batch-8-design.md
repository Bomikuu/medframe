## 1. Analytics workspace

Add `/clinic/analytics`, linked from the workspace when the user has at least one supported reporting permission. Use the incumbent white/navy/teal Operate design, restrained charts with exact accessible tables, permission-specific sections, real empty/error states and no fabricated sample figures. Filters select an authorized branch and7/30/90 completed clinic-local days; compare the immediately preceding equal-length period. Clearly label the excluded in-progress day and the as-of timestamp. Monetary values use the existing PHP/native currency projection and integer/Decimal arithmetic; never sum different currencies.

- **Operations:** appointments scheduled in the selected period, broken down by native current status; daily appointment volume; count of distinct patients with those appointments; consultation queue tickets admitted in the selected period by current status. Operations access requires existing operations.read and the member's branch scope. Counts are labelled current status, not a claim that cancellation/reschedule happened during that period. Do not infer no-shows or waiting time from appointment timestamps. Department visits remain separate from consultation queue tickets; no double-counted unified visit KPI.
- **Clinical workload:** consultations created during the period, current draft/in-progress/completed/finalized breakdown and provider-specialty grouping. Use only scoped_patients(...patients.clinical.read), including live patient grants; identify the report as "Patients you can access". This is a workload measure, not a clinical outcome, treatment-success score or finalized-event trend. Administrators without clinical grants do not gain this section or diagnosis/notes exposure. No diagnosis/reason free-text analytics in this milestone.
- **Finance:** reuse existing audited financial_overview and due projection for closed-day issued charges, actual received/refunded/net comparisons, current receivables and aging. Separate event-period totals from the current balance snapshot and due/future installments. Existing billing.read governs the section independently of operations/clinical access. Do not allocate invoice revenue to specialties or providers when the authoritative ledger does not record that attribution.
- Percentage changes are omitted/labelled "No prior baseline" if the prior total is zero; zero versus zero is "No change". Numeric missing data stays unavailable, not zero. Aggregate table CSV export includes only the report fields and filters visible to that requester, not patient-level rows; escape spreadsheet formula prefixes in textual cells. Existing audits record reads/exports and filter metadata without patient lists.

Charts are descriptive. No population, safety or outcome conclusion, staffing recommendation or future cash forecast is generated.

## 2. Specialty workspaces on the existing consultation owner

The existing onboarding catalog already contains general medicine/dental specialties, including Pediatrics, Dermatology and Orthopedics. The gap is that consultation template validation currently accepts only general_medicine/dentistry/other. Connect this catalog to template selection rather than introducing a second clinical record system.

- Add clinic specialty management after onboarding, using existing MedicalSpecialty/OrganizationSpecialty references and organization.manage. Support the existing catalog's active entries, without treating a checkbox as professional credential verification. Preserve existing clinic/provider codes and historical template definitions. Removing a clinic selection hides it from new choices; it never deletes existing templates, providers, encounters or revisions.
- Extend new template specialty selection using active clinic specialties plus the legacy general_medicine/dentistry/other values. Existing saved templates remain readable; historical TemplateRevision definitions are immutable. Existing encounters.write authoring/apply permission and exact-version/idempotent template owners remain. Provider specialty is not silently rewritten from a clinic selection or template.
- Provide optional editable starter forms for Pediatrics, Dermatology and Orthopedics. A clinician explicitly copies a starter into a clinic template; nothing is auto-seeded into original clinics. Use only documentation prompts such as reason for visit, relevant history, examination observations, assessment and plan, plus optional measurement labels with no invented findings, normal ranges, dosage, diagnosis, screening rule or automated advice. Prompts never populate patient values. Applying a template adds guidance through the existing owner without replacing saved SOAP text, signing a record or finalizing a visit.
- The consultation picker can filter by specialty and show a clear generic fallback. Dental/anatomy continue sharing their existing editor/aggregate; no new 3D anatomy or specialty-specific clinical algorithms are implied.

## 3. Reviewed local clinical export

Add an Export record action in the existing permitted consultation history view. The first exchange format is `medframe.clinical-export/1`, a documented JSON envelope and checked-in JSON Schema. This is a native Medframe export, labelled as such in the UI and documentation. No FHIR badge or unverified code-system mapping.

- Staff realm, completed MFA, live encounters.write/documents.write membership and native require_encounter/patients.clinical.read authorization are required. A superuser/admin flag is not a bypass. Patient-realm, kiosk, display and delegated Station credentials cannot use this bulk-copy action. The existing explicit portal release path remains unchanged.
- Export one selected immutable EncounterRevision, never an in-progress draft. Show the patient, consultation, exact revision/author/time, selected sections and an explicit local-download acknowledgement before generation. Default sections: SOAP, diagnoses with their recorded certainty/codes and structured observations. Dental/anatomy/procedures are optional named sections from that exact same snapshot only. No unrelated patient history, current working draft or silently merged later revisions.
- Envelope identifies schema version, generated timestamp, source organization/branch, patient clinic reference and name, encounter/revision identity and recorded author. Clinical content preserves recorded source/certainty and coordinate/reference metadata where selected. Do not invent clinical coding, units or conversions. Dates/times retain their recorded timezone/ISO representation.
- A reviewed preview creates a short-lived10minute signed review proof bound to the staff user, organization, encounter, revision and section selection. The proof does not contain patient text and cannot replace live authorization. Download rechecks the current session/MFA/grants/device boundary; a revoked grant denies download even with a previously valid proof. Wrong user/tenant/revision/selection or expired/tampered proof is rejected.
- Return application/json attachment, a generic identifier-based filename, private/no-store headers and a5MiB bound. Do not persist a downloadable clinical bundle or create a public URL. Exclude document/diagnostic binaries, object keys, signed storage URLs, login material, payment entries and unpublished current history. Optional sections that cannot be mapped faithfully fail explicitly rather than disappearing silently. Audit selection/revision IDs and digest, not the clinical payload. The export is a local download initiated by the user; no outbound HTTP connector or external recipient.
- A technical format document describes each field, optional section, source mapping and version strategy. Future import must validate identity, provenance, duplicate handling and clinician review under a separately approved contract; uploading this file does not automatically mutate records.
