No onboarding product code, migrations or runtime changes have been made. Implementation will be one connected batch, executed natively without agents. ## Outcome and scope

A Medframe platform administrator invites a clinic. The recipient sees a distinct clinical-first introduction, verifies the invited email, completes a short resumable setup, creates or authenticates their administrator account, reviews the result and creates the clinic exactly once. The resulting workspace uses real branding and configuration, with an honest first-patient empty state and a persistent setup checklist.

Include invitation administration, email verification, server-side drafts and resume, all six setup steps, private draft logos, existing/new account handling and MFA, atomic completion, first-run dashboard, audit/expiry/cleanup and bounded verification. These are internal work packages of one delivery, not separate user handoffs. Exclude public websites, AI integration, live SMS, payment processing, advanced scheduling and a new staff-invitation subsystem. The brief explicitly defers individual staff invitations: the optional team checklist item must say that team invitations are upcoming and provide truthful provisioning guidance rather than a nonfunctional “Invite” action.

Next/Previous, labelled slide indicators, keyboard arrows, swipe gestures, Skip Introduction and Get Started work accessibly; focus never jumps on an autosave. “Learn more” opens factual in-flow product information, not a dead link. Store introduction completed/skipped on the server; verified returning users resume instead of seeing slides again. ## Invitation identity and lifecycle

Platform administration at `/platform/clinic-invitations` lives outside `WorkspaceProvider` so a platform operator does not need an arbitrary clinical clinic selected. Require an active MFA-verified staff session plus explicit `platform_administrator` role membership, or an active Django superuser for operational bootstrap. `is_staff` alone and clinic-administrator membership are insufficient. This platform authorization grants no patient-record bypass. Add an explicit current-user platform capability rather than trusting a hidden navigation item.

The shadcn Data Table provides bounded pagination, status filters, contact/email/clinic/sent/expiry columns, create dialog, resend and revoke with Sonner feedback. Use a seven-day default expiry, configurable from one hour to thirty days. Store only a digest of a cryptographically random 256-bit token. No raw tokens in table/query output, audit fields or logs. Creation/resend queues the actual link in the encrypted mail outbox; no automatic external email is sent by the agent during development.

Invitation presentation statuses: pending → opened → in progress → completed; expired/revoked terminate incomplete access. Compute expiration authoritatively on every operation rather than relying on a scheduled job. “Accepted” administration filtering means verified/in-progress invitations; do not introduce a conflicting second completed state. Completed links show a neutral completion/sign-in state and never authorize another organization creation.

Keep the requested `/onboarding/invite/[token]` landing route. Its minimal page exchanges the token through a same-origin CSRF-protected POST, immediately replaces the path with `/onboarding/setup`, and excludes third-party scripts, analytics, external assets and prefetch. Apply no-store/no-referrer and ensure runtime/proxy access logging redacts this token-bearing route. Path tokens still reach infrastructure before exchange; this must be acknowledged in the operations configuration, not dismissed as solved by browser history replacement.

Possession of the link opens the public introduction but does not authorize draft reads/writes or account creation. Send a six-digit email code only to the invitation recipient; no arbitrary recipient parameter. Hash code+challenge context with the existing keyed digest, expire in ten minutes, cap verification attempts at five, and apply shared IP/invitation throttles plus a resend cooldown. Resending invalidates the previous challenge. Bind successful proof to the invitation generation and Django browser session; rotate its key on verification. Mask the address before proof and use generic failure states without account-existence disclosure.

Verified setup grants expire after eight hours absolute or thirty minutes idle, and never outlive their invitation. Original invitation plus a new email proof restores the same server draft in another browser. After account association, additionally require the same authenticated user/MFA state; an invite holder cannot take over a previously bound account's draft. Password reset/auth-epoch changes invalidate account-bound proof. Revocation, cancellation, expiry and resend invalidate outstanding grants/challenges. Resend rotates the token, retains the draft for the same email, and never silently changes its owner. Changing the recipient requires a new invitation.

## Account and API architecture

Do not weaken `/graphql` or `/portal/graphql`. Add a dedicated `/onboarding/graphql` schema with limited unauthenticated bootstrap/reference operations; every draft operation resolves the verified, current session-bound invitation grant itself. Use the same same-origin Next proxy, CSRF/origin guards, bounded query validation, safe errors and Redis throttling. No arbitrary invitation/draft UUID is accepted as authorization. Return no secrets in reference queries or invitation administration queries.

Expose the brief's queries (`onboardingInvitation`, `onboardingSession`, `onboardingProgress`, `availableSpecialties`, `availableClinicTypes`, `brandingPresets`) and mutations (`verifyOnboardingInvitation`, `startClinicOnboarding`, `saveOnboardingStep`, the four typed step update aliases, `verifyOnboardingEmail`, `completeClinicOnboarding`, `cancelClinicOnboarding`). Add explicit request-code, intro-completion, account-challenge and resume-email operations where needed. All mutation paths use one set of domain services, not separate validation implementations. Platform invitation management stays behind staff GraphQL with platform authorization.

Account registration/sign-in extends the existing auth challenge/activation adapter pattern. Use native `User.objects.create_user`, Django password validators, authenticate and the existing MFA services; never set `is_staff`/superuser or a clinical role for the clinic administrator. Existing account credentials/MFA are reused unchanged. A narrowly scoped onboarding account entry can begin an existing user's challenge even without a current staff membership, but only with verified invited-email ownership. Preserve/rebind the onboarding proof safely across Django login/session rotation. Confirm active invitation, matching email, user/auth epoch and proof again when MFA completes. A new user may exist before completion, but no active clinic or membership exists yet.

Normalize account email using the existing identity conventions and resolve existing accounts without creating case-only duplicates. New first/last names compose the native display name; an existing account's name is preserved unless explicitly edited by its authenticated owner. Creating a clinic never resets an existing password, authenticator or recovery codes.

The account step acknowledges versioned, readable notices. No approved legal terms/privacy text currently exists in the repository. Local development will show clearly labelled development-use notices and record their versions; production must supply approved configured content rather than silently presenting these as approved legal terms. No legal/compliance certification is part of this work.

Save drafts with an expected version and one serialized client autosave queue. Debounce bounded fields; Continue marks a step complete only after full server validation. Structurally valid partial drafts may save without marking the step complete. Validation failures remain visible in memory, with no false saved status. Conflict responses preserve input and offer reload/review; stale responses cannot advance progress or overwrite newer changes. Save and Exit flushes the server write and exits only after confirmation. It never serializes a password; account secrets are cleared when leaving that step/session. Review completion revalidates all authoritative values and proof, not just completed-step flags.

## Branding and private logos

Reuse image signature/decode/re-encode safeguards: PNG/JPEG/WebP, maximum 2 MiB before/after encoding and 2048px per side, no SVG/animation/executable content. Draft upload/download endpoints require fresh onboarding proof, exact draft ownership and valid invitation. Private opaque keys remain out of unrestricted URLs. Preview a chosen image in memory while scanning; distinguish that local preview from server-saved clean state. Restore only authorized clean previews. Pending/unavailable/rejected scans cannot become active logos; allow explicit removal to finish without one.

On completion, promote a clean owned draft logo into the existing organization-scoped Document/DocumentVersion branding pipeline within the database transaction, preserving the private object key and checksum so no nontransactional storage move can produce a partial clinic. Cleanup never deletes promoted keys. Reuse `scan_stream` and bounded task payloads; do not weaken clinical document guards to accommodate a pre-organization file.

Extend the existing frontend/backend theme contract additively with `secondary`; keep `primary`, `accent` and old-brand defaults compatible. Onboarding defaults follow this new brief: primary `#0F2D4A`, secondary `#0EA5A4`, accent `#22C1B6`. Existing organizations retain their saved appearance. Apply accessible semantic foregrounds rather than white text on every chosen tint; retain the primary contrast guard. Both preview and final workspace use the same resolver/validation. No arbitrary CSS or global draft-theme mutation.

## Atomic completion and dashboard

Within one transaction, lock native user then invitation/draft in a consistent order, recheck current MFA/email proof and invitation, validate all typed data/logo/consents, and serialize clinic-name uniqueness checks including case-insensitive conflicts with existing clinics. Never attach a new administrator to an existing clinic solely on a matching name/email. Preserve existing database constraints; an unavailable name is a correctable conflict with the draft retained.

Create exactly one Organization, initial Branch, clinic-administrator Membership, branding/profile/specialties/provider-estimate/practice settings and checklist state. Do not add doctor/dentist roles or ProviderProfile from specialty/provider selections. Persist the completion result and consume the invitation in the same transaction. Unique invitation→draft/completion relationships and a request key make concurrent/retried completion return the same authorized result; altered payload under the same request key conflicts. Transaction failure rolls everything back; queued work uses on_commit. Revocation and completion lock the same records so only one can win. Completed-invitation revocation does not deactivate the already-created clinic.

Return the new organization/branch result and use the existing authenticated workspace loader with that explicit organization. Display completion, then navigate directly to `/clinic?organization=<id>` via Go to Dashboard or Register Patient. Show real checklist states and honest empty patient content; do not fabricate metric cards. Account/clinic/branding entries are complete, first patient derives from actual authorized records, optional template/settings entries link to working pages, team invitation is labelled upcoming. Persist per-user/per-organization dismissal, without changing other clinics' dashboards.

Ruff, Prettier, scoped lint/TypeScript/build and migration preservation checks are required. Log unrelated findings without repair.
