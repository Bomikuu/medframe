This version focuses on four important changes:
1. Django replaces FastAPI — using Django ORM, authentication, migrations, Django Admin, and Strawberry GraphQL.
2. Clinical-first development — doctors, patients, medical records, consultations, diagnoses, and interactive 3D dental charting come first.
3. White, customizable dashboard — professional, minimal, with configurable colors, typography, layouts, components, and clinic branding.
4. Batch-based implementation — implement multiple connected features together instead of completing only one minor feature per development cycle.
The first batch should produce a working clinical platform, not just authentication or dashboard mockups.

# 1. PROJECT OVERVIEW
# ============================================================

Build Medframe, a modern, secure, customizable healthcare
management platform designed for doctors, dentists, clinics,
patients, and healthcare organizations.

Project Name: Medframe
Repository: medframe
Tagline: The Foundation of Modern Care.

Medframe should function as a clinical operating system.

3. Clinical consultations
4. Medical records

Medframe is a clinical platform first.

# ============================================================
# 3. DEVELOPMENT APPROACH — BATCH IMPLEMENTATION
# ============================================================

IMPORTANT IMPLEMENTATION INSTRUCTION:

Do not implement only one tiny feature per development cycle.

Implement MULTIPLE RELATED FEATURES in each development batch.

A batch should represent a complete functional milestone.

For example:

BAD APPROACH:

Task 1:
Create patient database model.

Stop.

Task 2:
Create patient API.

Stop.

Task 3:
Create patient form.

Stop.

Task 4:
Create patient list.

Stop.

GOOD APPROACH:

BATCH: PATIENT MANAGEMENT

Implement together:

- Patient database models
- Patient registration
- Patient list
- Patient search
- Patient profile
- Medical history
- GraphQL queries and mutations
- Validation
- Authorization
- Relevant tests

The batch should be functional from frontend to database.

Each batch should include:

1. Database models
2. Django migrations
3. Backend business logic
4. GraphQL operations
5. Frontend pages and components
6. Validation
7. Authorization
8. Relevant tests
9. Integration verification

Implement multiple cohesive features in one batch.

Avoid stopping after creating only models,
only API endpoints, or only frontend mockups.

When a feature is straightforward, complete the surrounding
related functionality in the same batch.

Do not artificially split closely related changes
into numerous tiny tasks.

Do not ask for confirmation after every file or component.

Continue implementing the defined batch using reasonable
technical decisions.

However:

- Do not skip security requirements.
- Do not bypass validation.
- Do not sacrifice data integrity.
- Do not invent clinical information.
- Do not implement unrelated future modules prematurely.
- Do not claim a feature works without verifying it.

If a dependency or technical limitation blocks a feature,
complete the remaining feasible functionality and clearly
identify the blocker.

# 8. SECURITY AND PATIENT CONFIDENTIALITY
# ============================================================

SECURITY IS NON-NEGOTIABLE.

Medframe handles sensitive patient information.

Implement security from the beginning.

AUTHENTICATION:

Use Django authentication as the foundation.

Create a custom User model from the beginning
if additional identity fields are needed.

Support:

- Login
- Logout
- Secure sessions
- Account recovery
- MFA for clinical and administrative staff
- Session revocation
- Rate limiting

Use secure HTTP-only cookies.

Configure CSRF protection correctly for
GraphQL mutations and session-based authentication.

Do not store authentication credentials
in localStorage.

AUTHORIZATION:

Implement organization-scoped access control.

Support:

- Platform Administrator
- Clinic Administrator
- Doctor
- Dentist
- Nurse
- Receptionist
- Patient

Enforce:

- Role permissions
- Organization membership
- Patient relationship authorization
- Resource-level access restrictions

A doctor must not automatically access
every patient's records.

A clinic must not access unrelated organizations' data.

Receptionists must not automatically have access
to detailed clinical notes.

Do not rely on frontend permissions alone.

DATA PROTECTION:

- HTTPS/TLS
- Encryption at rest
- Encrypted backups
- Private document storage
- Secure secrets
- No patient data in application logs
- Appropriate retention controls

AUDIT LOGGING:

Track:

- Medical record access
- Medical record modification
- Diagnosis updates
- Consultation finalization
- Treatment updates
- Document access
- Permission changes

Preserve finalized clinical information.

Support authorized amendments rather than
silently overwriting historical records.

Design for applicable Philippine data privacy
requirements, including sensitive health information.

Do not claim legal compliance without appropriate review.

My additional recommendations
There are three implementation decisions I would make from the beginning.
1. Treat theme customization as a proper application module
Instead of scattering theme configuration throughout Next.js, create a dedicated branding Django application.
For example, the organization can store settings equivalent to:
interface MedframeTheme {
  branding: {
    organizationName: string;
    logoUrl?: string;
    primaryColor: string;
    secondaryColor: string;
    accentColor: string;
  };

  appearance: {
    mode: "light" | "dark" | "system";
    fontFamily: string;
    borderRadius: "none" | "small" | "medium" | "large";
    density: "compact" | "comfortable" | "spacious";
  };

  layout: {
    sidebar: "expanded" | "collapsed";
    sidebarWidth: number;
    contentWidth: "contained" | "full";
    headerStyle: "standard" | "compact";
  };
}

This is a conceptual frontend type; the actual values should be validated against Django models and stored securely.
The app reads the effective configuration and applies CSS variables.
This lets each clinic customize its appearance without rebuilding or redeploying the application.
2. Keep the dashboard genuinely white
Based on your preference for minimal, professional interfaces, I would use the following default appearance.
Element	Default
Page background	#FFFFFF
Sidebar	#FFFFFF
Header	#FFFFFF
Cards	#FFFFFF
Borders	#E2E8F0
Primary text	#1E293B
Primary actions	#0F2D4A
Interactive accents	#0EA5A4
Font	Inter
Shadows	Minimal
Gradients	None by default
Components	shadcn/ui


White should be the dominant background, with borders and typography creating hierarchy. Reserve stronger colors for actions, selected states, and important information.
3. Integrate the 3D dental model with the consultation
I would avoid treating the dental model as a completely separate record-editing application.
Instead, make it available directly within the clinical consultation workspace.
For example:
MEDFRAME
└── Clinical Workspace
    │
    ├── Patient Overview
    │
    ├── Current Consultation
    │
    ├── Dental Chart
    │   ├── Interactive 3D Model
    │   ├── Tooth Selection
    │   ├── Clinical Findings
    │   ├── Tooth Conditions
    │   └── Treatment History
    │
    ├── Clinical Notes
    │
    ├── Diagnosis
    │
    ├── Procedures
    │
    ├── Treatment Plan
    │
    └── Medical Documents

When the dentist clicks a tooth and records a finding, that record should immediately become part of the current encounter's draft. Once the encounter is finalized, the findings become part of the patient's clinical history.
This avoids having separate, inconsistent records between the 3D model and the consultation.
The intended outcome of Batch 1 is a functioning Medframe clinical workspace with multiple connected capabilities—not a collection of disconnected pages.
