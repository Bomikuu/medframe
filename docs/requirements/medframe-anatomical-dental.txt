# MEDFRAME — COMPLETE 3D DENTAL MODEL REPLACEMENT

## Objective

Completely replace the current procedurally generated
dental model with realistic anatomical 3D tooth models.

The existing dental model looks unrealistic.

Teeth currently resemble generic rounded blocks,
with incorrect or simplified dental anatomy.

This is unacceptable for the intended clinical experience.

Medframe needs a professional, anatomically representative
dental visualization system with interactive teeth.

IMPORTANT:

Do not attempt to fix the problem only through
CSS, colors, shadows, lighting, or camera settings.

The underlying tooth geometry must be replaced.

Use actual 3D dental assets.

Do not recreate teeth using primitive geometries.

Do not generate all teeth from the same generic shape.

---

# 3. Asset Inspection

Before replacing the current renderer,
inspect available dental assets.

Determine:

- File format
- Mesh count
- Object hierarchy
- Whether individual teeth are separate
- Tooth morphology
- Crown and root geometry
- Mesh orientation
- Object scale
- Material properties
- Polygon count
- Available textures
- Licensing information

If using an existing complete dentition model,
verify that individual teeth can be selected.

If the model contains a single fused mesh,
prepare a separated version.

Use individual tooth models if needed.

---

# 4. Prepare Anatomical Models

Use Blender or another appropriate
3D asset processing tool.

Prepare a complete permanent dentition.

Required:

- 32 permanent teeth
- Anatomically appropriate incisors
- Anatomically appropriate canines
- Anatomically appropriate premolars
- Anatomically appropriate molars
- Realistic dental arches
- Appropriate tooth proportions
- Correct upper/lower placement
- Correct left/right identification

Do not create the entire dental arch
by arranging identical tooth models.

Each tooth type must retain its
distinct anatomical morphology.

Use left- and right-specific anatomical
models where available.

Mirroring representative models may be used
only as an explicitly documented approximation
and must be reviewed for anatomical suitability.

Standardize:

- Model scale
- Coordinate system
- Rotation
- Orientation
- Object origin
- Object naming

Use clinically appropriate anatomical dimensions.

Do not arbitrarily stretch teeth to fit a layout.

Prepare the models as reusable assets.

---

# 5. Complete Dental Arch

Create a realistic upper and lower dental arch.

The teeth should follow a natural curved arrangement.

Do not place teeth in straight rows.

Ensure:

- Correct anterior tooth arrangement
- Proper canine positioning
- Correct premolar placement
- Correct molar placement
- Appropriate tooth angulation
- Reasonable spacing
- Appropriate upper/lower relationship

Support 32 permanent teeth.

Use FDI numbering.

UPPER RIGHT:
18, 17, 16, 15, 14, 13, 12, 11

UPPER LEFT:
21, 22, 23, 24, 25, 26, 27, 28

LOWER LEFT:
31, 32, 33, 34, 35, 36, 37, 38

LOWER RIGHT:
41, 42, 43, 44, 45, 46, 47, 48

Important:

Validate anatomical left and right from
the patient's perspective.

Do not confuse screen-left and screen-right
with anatomical left and right.

Ensure model selection matches the
existing dental chart numbering.

# 7. Interactive Tooth Selection

Every individual tooth must be clickable.

When a tooth is selected:

1. Identify the correct FDI tooth number.
2. Highlight the selected tooth.
3. Update the selected tooth state.
4. Display the tooth information panel.
5. Load existing findings from the backend.
6. Allow permitted clinical interactions.

Example:

Selected Tooth: 16

Name:
Upper Right First Molar

Existing Findings:
Dental Caries

Affected Surface:
Occlusal

Treatment:
Filling Recommended

Selected teeth should have a clear visual state.

Avoid permanently changing the original
tooth material when selection changes.

Preserve original materials and restore them
when deselected.

Use raycasting or React Three Fiber
pointer events for interaction.

Prevent clicks from selecting unrelated meshes.

---

# 8. Tooth Surface Selection

Support recording findings against:

- Mesial
- Distal
- Buccal / Facial
- Lingual / Palatal
- Occlusal / Incisal

IMPORTANT:

Do not assume the imported meshes
already contain surface segmentation.

Inspect available geometry.

If separate surface meshes or reliable
surface mappings exist, use them.

If not, provide a conventional 2D surface
selector linked to the selected 3D tooth.

Do not fabricate clinically precise surface
selection from unreliable mesh geometry.

Store tooth surface identifiers independently.

---

# 9. Dental Condition Visualization

Support visual representations of
clinically recorded conditions.

Examples:

HEALTHY

Display original tooth material.

MISSING TOOTH

Hide the affected tooth.

CARIES

Highlight or annotate the affected region.

FRACTURE

Display a visible fracture annotation
or a validated alternative tooth mesh.

FILLING

Display a restoration overlay where supported.

CROWN

Display a crown model or suitable
restoration representation.

IMPLANT

Display an appropriate implant model.

ROOT CANAL

Indicate completed root canal treatment
through appropriate clinical visualization.

GUM INFLAMMATION

Highlight the documented gum region.

IMPORTANT:

Do not automatically deform the tooth
using arbitrary geometry.

Use predefined anatomical variants,
surface overlays, or clinical annotations.

The visual representation must reflect
stored clinical information.

Distinguish:

- Existing conditions
- Proposed treatments
- Completed treatments
- Educational previews

Do not modify the original clinical state
when previewing proposed treatments.

# 10. Materials and Rendering

Improve visual realism.

Use physically based materials.

Teeth should have:

- Appropriate enamel coloration
- Subtle material variation
- Natural shading
- Visible anatomical morphology
- Balanced lighting

Avoid:

- Plastic-looking teeth
- Excessive shininess
- Unrealistic glow
- Strong gradients
- Cartoon-like appearance
- Overly dark shadows

Use a restrained clinical visualization style.

The model should resemble professional
dental education or clinical charting software.

Prioritize anatomical readability
over photorealistic decoration.

# 13. Backend Integration

Preserve existing Django dental records.

The model must use the existing
clinical data architecture.

Each tooth should map to its
corresponding FDI identifier.

When selecting a tooth:

- Retrieve current findings
- Retrieve recorded conditions
- Retrieve procedures
- Retrieve treatment history

When recording a finding:

1. Validate permissions.
2. Associate the finding with the patient.
3. Associate it with the relevant encounter.
4. Save it through GraphQL.
5. Persist it in PostgreSQL.
6. Update the dental model.
7. Display success feedback.

Do not store diagnoses inside GLB files.

Do not treat frontend materials
as authoritative clinical data.

Do not silently overwrite finalized
clinical records.

# 15. Performance Optimization

Realistic dental geometry must not
make the application unnecessarily slow.

Use:

- Optimized GLB assets
- Shared materials
- Appropriate texture sizes
- Mesh compression
- Asset preloading
- Lazy loading
- GPU-conscious rendering
- Geometry reuse where suitable

Preserve enough geometry for tooth
morphology to remain recognizable.

Do not over-optimize until tooth
anatomy becomes visibly inaccurate.

Avoid downloading the same model repeatedly.

Do not load dental assets on unrelated pages.

Test on desktop and mobile devices.

# 17. Missing Assets and Fallbacks

If the actual dental models are unavailable:

1. Inspect the repository for existing assets.
2. Identify the missing files.
3. Document the required format.
4. Provide instructions for obtaining them.
5. Prepare the asset loading architecture.
6. Implement applicable clinical and UI integrations.

Do not silently recreate procedural block teeth.

Do not claim the realistic model is complete
without loading actual anatomical assets.

A temporary schematic model may remain
only if explicitly labeled as a placeholder.

Keep the existing working clinical functionality
until the replacement is ready.

# 18. Acceptance Criteria

The task is complete when:

- Real anatomical tooth meshes replace primitive teeth.
- All 32 permanent teeth are represented.
- Incisors, canines, premolars, and molars look distinct.
- Dental arches are naturally curved.
- Tooth numbering is correct.
- Teeth are individually selectable.
- Selected tooth information is accurate.
- Upper/lower jaw controls work.
- Tooth isolation works.
- Camera framing is appropriate.
- Saved clinical conditions load correctly.
- Missing teeth can be represented.
- Recorded findings can be visualized.
- Clinical edits persist in PostgreSQL.
- Historical findings remain accessible.
- The viewer works responsively.
- The 2D fallback remains functional.
- Third-party asset licenses are documented.
- Patient confidentiality is preserved.

Do not consider the task complete merely
because the model renders.

The anatomy, interactions, numbering,
and clinical persistence must all work.
