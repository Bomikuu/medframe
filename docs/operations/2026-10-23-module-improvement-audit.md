# Medframe module improvement audit — October 23, 2026

## Scope and conclusion

This is a source and historical-evidence audit of the 28 frontend feature modules, 63 page routes, the model inventory of 20 backend applications, and selected workflow/transport services. It reviews module entry points, shared interactions, persistence boundaries and the existing error register. It is not a line-by-line review of every source file, a live browser sweep, a security certification or clinical validation.

The application was already stopped after disk cleanup. It remains stopped; no source changes, builds, automated tests, lint, typechecks, database writes, external messages or public deployment occurred. Only this audit, the error-register cross-reference and a private source-only graph were written.

The main recommendation is to improve continuity across existing modules before expanding the feature count. Medframe already has extensive clinical, scheduling, financial, registration, Station and online-room capabilities. Several historical findings are acceptance gaps rather than current defects; they must not be described as newly reproduced bugs.

Priorities: **P1** daily workflow/reliability or integration ambiguity; **P2** usability and operational depth; **P3** later expansion. No new critical vulnerability was established by this review.

## Backend and operational recommendations

- **Accounts / organizations / providers:** keep separate realm, membership, branch, patient-grant and Station-session boundaries. Effective-access/readiness summaries should explain current rules, not bypass them. New screens must reuse the existing permission owners.
- **Encounters / dental / anatomy / treatments / patients:** preserve version checks, immutable finalized records, attributed amendments and one clinical aggregate. Refactors must retain saved drafts and editing transfer behavior.
- **Billing / services / operations:** preserve transaction/idempotency boundaries and distinguish appointments, visits, department tickets, service agreements and financial obligations. Avoid introducing a second independent status ledger in the UI.
- **Documents / portal / diagnostics:** maintain scan gating, exact-version release, withdrawal and protected downloads. A convenient photo or preview must not broaden clinical record access.
- **Auditing / communications / onboarding / stations / websites / branding:** make important outcomes understandable in the UI and correlate them with existing native audit/event history. Do not expose internal identifiers or private audit contents publicly.
- **Resource use:** keep heavy 3D/media loading separate from everyday directory/report work. First measure the actual loaded route and inactive model resources; directory size is not proof of browser memory usage.
- **Backup retention:** the requested manual cleanup is already complete. Define future retention rules so repeated full Git/database checkpoints do not accumulate again; retain approved migration/baseline recovery points and verify recent backup integrity before pruning. Generated development files will grow again during compilation. Do not delete original storage or restore-rehearsal databases as an incidental UI improvement.

## Recommended implementation phases

1. **Shared reliability and identity:** M01–M04/M07, common search/clear behavior, authorized photos, stable loading/retry and URL-backed navigation. Acceptance: typed searches remain responsive, back navigation restores context, refresh keeps focus, and clinic changes clear prior-scope data.
2. **Clinical continuity:** patient first-screen priorities, draft resume/save/conflict status, documents, diagnostic ownership, treatment follow-ups and dental/anatomy selection clarity. Acceptance: one patient can move through the connected visit without losing notes or confusing saved versus historical data.
3. **Clinic operations and Stations:** schedules/overrides, appointments/rescheduling, queue transfers, staff/provider readiness, device lifecycle and terminal idle/connection recovery. Acceptance: reception-to-doctor-to-cashier handoff preserves one visit and correct access; staff appointment/queue updates remain manual.
4. **Financial clarity:** service/agreement preview, installment obligations, allocation/refund traceability, cashier closing and financial comparison definitions. Acceptance: all figures reconcile to the native ledger and money-recording actions retain current permissions/idempotency.
5. **Patient communication and online care:** task-first portal, registration/invite readiness, M05/M06, delivery outcomes and real two-party call continuity. External SMS, public internet media and payment-provider integration each require their own configured/authorized rollout; this audit does not activate them.
6. **Administration and maintainability:** account/security explanations, specialty/template previews, website publication checks, measured 3D/media performance, focused editor decomposition and documented backup retention. AI remains a later explicitly authorized feature.

Phases deliver multiple related improvements. Start with Phase 1 rather than another broad visual redesign. Keep verification bounded and tied to each changed workflow; do not reopen every historical test gap in one cycle.
